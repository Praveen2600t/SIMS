# SICMS System Architecture & Engineering Guide

## 1. Overview
The **Smart Inventory Intelligence System (SICMS)** is an enterprise full-stack web application designed for continuous monitoring and supply chain management across agricultural mandis, food retailers, and supermarkets in **Tamil Nadu, India**.

The system provides real-time stock surveillance, transaction-level consistency, automated batch expiry tracking, and explainable rule-based anomaly detection across 18+ Tamil Nadu districts (e.g., Koyambedu Wholesale Market, MGR Mandi Coimbatore, Mattuthavani Madurai, Shevapet Salem).

---

## 2. Technology Stack
* **Frontend**: Next.js 16 (App Router), React 19, TypeScript
* **Styling**: Tailwind CSS
* **Data Visualization**: Recharts
* **Backend API**: Next.js App Router Server Route Handlers
* **Database & ORM**: PostgreSQL via Prisma ORM 6
* **Validation**: Zod (Type-safe input and query verification)
* **Authentication**: Edge-compatible JWT (`jose`), password hashing (`bcryptjs`), and HTTP-only session cookies
* **Testing**: Vitest with sequential execution (`pgbouncer=true`)

## 3. Database Design & Consistency
The database utilizes a fully normalized relational schema:
* `users`: Authentication records, RBAC roles (`ADMIN`, `STAFF`), and status.
* `categories`: 10 core categories (Vegetables, Fruits, Beverages, Fast-food ingredients, Grains/staples, Dairy, Bakery, Spices, Meat/frozen, Grocery/packaged).
* `locations`: Tamil Nadu mandi hubs, central distribution centers, and retail trade centers.
* `suppliers`: Verified sample regional vendors with ratings and regional districts.
* `products`: Master product catalog with SKU codes, categories, prices, units, and configurable alert thresholds (`minStockLevel`, `reorderQuantity`).
* `inventory_batches`: Per-batch shelf life and expiry dates (`expiryDate`, `batchNumber`, `quantity`, `status`).
* `stock_movements`: Immutable transaction journal recording all stock changes (`IN`, `OUT`, `ADJUSTMENT`, `SALE`, `DAMAGE`, `RETURN`, `AUDIT`).
* `sales` & `sale_items`: Invoicing, customer details, and counter sale receipts.
* `purchase_orders` & `purchase_order_items`: Inbound procurement orders and delivery receiving.
* `alerts`: Operational alerts generated by the Continuous Monitoring Engine.
* `audit_logs`: User-attribution tracking for all sensitive and state-changing actions.

### Consistency Guarantees
1. **Zero / Negative Stock Prevention**: In `InventoryService.processStockOut`, the server transaction reads current product balance and strictly rejects transactions if `requested_quantity > available_quantity`.
2. **Atomic Invoicing**: In `POST /api/sales`, the sale record and individual stock movements are committed in sequence, deducting inventory in the same transaction block.
3. **Audit Trail**: Every mutation records previous quantity, new quantity, movement type, reason, and authenticated user ID.

## 4. Continuous Monitoring Engine Architecture
The monitoring engine (`MonitoringService`) runs autonomously on stock mutations or via scheduled triggers (`/api/monitoring/run`):

1. **OUT_OF_STOCK**: Triggered when `currentQuantity <= 0`.
2. **LOW_STOCK**: Triggered when `0 < currentQuantity <= minStockLevel`.
3. **EXPIRY_WARNING**: Evaluates active batches expiring within a configurable window (default: 7 days).
4. **EXPIRED**: Flags batches where `expiryDate < now()`, marks batch status as `EXPIRED`, and issues critical alert.
5. **Auto-Resolution**: When stock is replenished or condition is rectified, existing open alerts are updated to `RESOLVED` with an explanatory note.
6. **Rule-Based Anomaly Detection**:
   * Sudden quantity deductions (> 40% of stock in a single movement without a sales reference).
   * Frequent manual adjustments (3 or more audit adjustments in recent history).

## 5. Security & Authorization
* Server-side authentication enforced via `requireUser` and `requireAdmin` in `src/lib/auth.ts`.
* Non-admin users are restricted from archiving products or manipulating system settings.
* Passwords hashed using bcrypt with salt rounds of 10.
* Session tokens stored in HTTP-only, SameSite lax cookies.
